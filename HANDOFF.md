# Handoff notes

What changed on `claude/site-code-best-practices-6rs7nm`, and what a tool or
person picking the repo up afterwards has to do differently. Written for work
that was already in flight against the old layout.

Nothing about the site's behaviour, design or data changed. Every review,
brewery, location and rating is byte-for-byte what it was; the files they live
in moved.

---

## 1. `script.js` no longer exists

It was 3,237 lines: the first ~400 were the reviews, the rest was rendering.
It is now two files, loaded in that order by `index.html`:

| File | Holds | Roughly |
|------|-------|---------|
| `data.js` | Every review, brewery, location, brand domain, Untappd average and watchlist entry. No behaviour. | 422 lines |
| `app.js` | Statistics, tables, charts, maps, search, the command palette. No beer data. | 2,744 lines |

Git records this as a rename (`script.js` → `app.js`, ~70% similar) plus a new
`data.js`.

**If you have uncommitted or unmerged edits to `script.js`:** they will not
apply cleanly. Which half of the split your change belongs in decides what to
do:

- **You added or edited beer data** (a review, a brewery, a `BRAND_DOMAINS`
  entry, a country in `FLAGS`/`CNAMES`) — reapply it to `data.js`. Then run
  `npm run check && npm run export` and commit `data/` alongside it.
- **You changed rendering, stats or layout** — reapply to `app.js`. Line numbers
  shifted by roughly −400 for everything below the old data block.
- **You changed both in one commit** — split it. The whole point of the new
  layout is that those two kinds of change stop touching the same file.

`index.html` changed correspondingly:

```html
<!-- was -->
<script defer src="script.js"></script>

<!-- now — order matters, and `defer` preserves it -->
<script defer src="data.js"></script>
<script defer src="app.js"></script>
```

## 2. Google Sheets is gone — do not rebuild it

This is the change most likely to invalidate in-flight work, so here is the full
picture.

### What was removed

| Thing | What it was |
|-------|-------------|
| `SHEETS_CONFIG` in `script.js` | `{enabled, sheetId, beersTab, breweriesTab, locationsTab}` |
| `loadFromGoogleSheets()` | An IIFE that fetched three published tabs from the `gviz/tq?tqx=out:csv` endpoint, parsed the CSV by hand, and replaced `beers` / `breweries` / `drunkLocs` |
| `SHEETS_SETUP.md` | Instructions for publishing a sheet and pasting its ID |
| `sheets/*.csv` + `sheets/DATA_ENTRY_GUIDE.md` | Seed CSVs and a formula-driven data-entry workbook |

### Why

It was never switched on — `enabled` was `false` and `sheetId` was empty, so the
loader returned on its first line every time the page loaded. Meanwhile the
seed CSVs had drifted badly out of date: `sheets/beers.csv` held **52 reviews
against the real 79**, and `sheets/breweries.csv` held **32 breweries against
the real 65**. Anyone who had turned the integration on would have silently
replaced two thirds of the site's data with a stale copy.

It was also a second store competing with `data.js` for the title of source of
truth, which is the thing the rest of this branch exists to settle.

### What replaces it

**`data.js` is the store.** `data/` holds generated exports of it — that is the
import path for a database, and it is regenerated by `npm run export`, never
hand-edited.

**If the plan was to host the data in Sheets:** drop it. Import `data/*.json`
into a real database instead — the JSON is already table-shaped, one file per
table. If a spreadsheet is still wanted for hand-entry, generate it from the
database; do not make it the source.

## 3. The runtime integration surface

`data.js` declares its three collections with `let`, specifically so a host can
replace them:

```js
let beers      = [ /* … */ ];   // one entry per pour
let drunkLocs  = [ /* … */ ];   // every city a review was logged in
let breweries  = [ /* … */ ];   // where each beer is made
```

To drive the existing page from an API or a database, replace their contents and
call one function:

```js
const rows = await fetch('/api/beers').then(r => r.json());
beers.length = 0;
beers.push(...rows);
reloadData();          // app.js
```

`reloadData()` recomputes every derived statistic, clears the lazy-render guards
so each tab redraws, and repaints whatever tab is open. Nothing else in the app
caches data across that call. That function is the entire integration surface —
there is no other hook to find.

## 4. The data, as tables

Generated by `npm run export`. Both JSON and CSV for the three main tables;
JSON only for the rest.

**`data/beers.json`** — 79 rows, one per pour. `beer` is **not** unique across
rows: the same beer drunk twice is two rows, and the site's ratings are averages
over them.

```json
{
  "beer": "Grolsch", "style": "Pilsner",
  "origin": "NL", "originCountry": "Netherlands",
  "abv": 5, "method": "Bottle",
  "city": "Hengelo", "region": "Overijssel", "country": "Netherlands", "cc": "NL",
  "rating": 3.5, "isNew": false,
  "month": "Jan", "monthN": 1, "year": 2026
}
```

**`data/breweries.json`** — 65 rows. In `data.js` a brewery's beers and ratings
are two `·`-separated strings read positionally; the export pairs them so the
pairing cannot be lost.

```json
{
  "name": "Hofbräu München", "location": "Munich, Bavaria",
  "country": "Germany", "cc": "DE", "lang": "de",
  "lat": 48.1351, "lng": 11.582,
  "beers": [
    {"beer": "Hofbräu Münchner Weiße", "rating": 4.75},
    {"beer": "Hofbräu Dunkel", "rating": 2.75}
  ]
}
```

**`data/locations.json`** — 27 rows: `{city, region, country, cc, lat, lng}`.

Plus `brand-domains.json` (beer → the domains its logo is looked up from),
`untappd-averages.json` (the world's average per beer, for the contrarian
chart) and `watchlist.json` (beers not yet reviewed).

**Join keys**

- `beers.beer` → `breweries.beers[].beer`
- `beers.city` + `beers.cc` → `locations.city` + `locations.cc` (city alone is
  not unique across countries)
- `beers.origin` and `*.cc` are ISO 3166-1 alpha-2, **except** the UK, which is
  split into `GB-ENG` / `GB-SCT` / `GB-WLS` / `GB-NIR`. A schema with a strict
  2-character country column will reject those four.

## 5. Things that will now fail a build that used to pass

- **CI validates the data.** `.github/workflows/validate-data.yml` runs
  `npm run check` on every push and pull request. It fails on a missing or
  wrong-typed field, a rating that isn't 0–5 in quarter steps, a country code
  with no flag or name, a beer no brewery lists, a beer with no
  `BRAND_DOMAINS` entry, a consumption city missing from `drunkLocs[]`, a style
  with no colour in `sC`, and on `data/` being out of step with `data.js`.
  It needs nothing installed — no `node_modules`, no lockfile.
- **`data/` must be regenerated and committed** whenever `data.js` changes.
  `npm run export` does it; the check above enforces it.
- **Every value interpolated into `innerHTML` goes through `esc()`.** A beer
  named `Smithwick's` closes an attribute early otherwise. Two deliberate
  exceptions: Chart.js labels and tooltips (canvas text is drawn, not parsed)
  and values that are already HTML.
- **The CDN tags are hash-locked.** Chart.js and Leaflet load from jsDelivr at
  an exact version with an `integrity` hash. Changing a version means running
  `npm run sri -- --write` — a hand-written or stale hash means the browser
  refuses the file and the charts or the map simply never appear.

## 6. Commands

None of these need an install except `smoke`.

| Command | Does |
|---------|------|
| `npm run check` | Validates the data and confirms `data/` matches `data.js` |
| `npm run export` | Regenerates `data/` from `data.js` |
| `npm run sri` | Re-derives the CDN integrity hashes from the npm registry (`-- --write` to fix) |
| `npm run smoke` | Drives the real page in headless Chromium (needs `npm install`) |

`CLAUDE.md` holds the full rules — how to add a beer, the ranking threshold, the
design tokens. `README.md` is the short version.
