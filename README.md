# Jwal's Brew Reviews

A running log of every beer I drink — ratings, places and trends. A static site:
open `index.html` and it runs. There is no build step, no framework and no
server.

The reviews are added in the [beer-review-buddy](https://github.com/jwal64/beer-review-buddy)
app and live in the Supabase database behind it. This repo renders them.

## The files

| File | What it is |
|------|------------|
| `index.html` | The page. Every panel's markup, and the three `<script>` tags. |
| `data.js` | **The store**, generated by `npm run sync` from the database. Every review, brewery, location and brand domain. No behaviour. |
| `app.js` | Everything the data does: stats, tables, charts, maps, search. No data. |
| `style.css` | The design system. `:root` is the only place a colour is written. |
| `data/` | Generated exports of `data.js` as JSON and CSV — see below. |
| `tools/` | Plain Node scripts. No dependencies, nothing to install. |
| `logos/` | Optional local logo files for beers whose brand no logo service knows. |

Chart.js and Leaflet load from a CDN, pinned to an exact version and locked to a
`integrity` hash, so a compromised CDN can't swap the library out.

## Working on it

**A beer is added in the [beer-review-buddy](https://github.com/jwal64/beer-review-buddy)
app, not here.** That app writes to a Supabase database, and that database is the
source of truth for the whole log. `data.js` is generated from it:

```sh
npm run sync      # rewrite data.js from the database
npm run check     # every rule CLAUDE.md states, enforced
npm run export    # refresh data/ to match
```

`npm run sync` needs `SUPABASE_URL` and `SUPABASE_KEY` (the publishable one) in
the environment. Nobody normally runs it by hand: the **Sync from Supabase**
workflow does all three nightly and commits the result, so a beer logged on a
phone reaches the site on its own.

Editing `data.js` is not how you add a beer. The file says so at the top, and
the next sync overwrites whatever was written there.

`npm run check` still needs nothing installed — it is Node and the repo. It runs
on every push (`.github/workflows/validate-data.yml`), so a review that came out
of the database with a country code that has no flag, a brewery that lists no
beers or a missing brand domain fails the build instead of quietly rendering
wrong. The database enforces most of the same rules itself, at the moment the
row is written.

| Command | What it does |
|---------|--------------|
| `npm run sync` | Rewrites `data.js` from the Supabase tables (`-- --check` to test without writing) |
| `npm run check` | Validates the data and confirms `data/` is in step with `data.js` |
| `npm run roundtrip` | Sends the data out through the database columns and back, and fails if a value is lost |
| `npm run export` | Regenerates `data/` from `data.js` |
| `npm run seed` | Regenerates the SQL that seeded the database from `data.js` (the one-time cutover) |
| `npm run sri` | Re-derives the CDN `integrity` hashes from npm (`-- --write` to fix them) |
| `npm run smoke` | Opens the page in a real browser and checks it works (needs `npm install`) |
| `npm run logos` | Checks every beer actually resolves a logo, against the live CDNs (needs `npm install`) |

## The data

The Supabase database behind beer-review-buddy is the source of truth. `data.js`
is written from it by `npm run sync`, and `data/` holds the same rows again in
formats other software can read, regenerated by `npm run export`:

| File | Shape |
|------|-------|
| `data/beers.json` · `.csv` | One row per pour. `beer` is not unique — the same beer drunk twice is two rows. |
| `data/breweries.json` · `.csv` | One row per brewery, with its beers and their ratings paired up. |
| `data/locations.json` · `.csv` | Every city a review was logged in, with coordinates. |
| `data/brand-domains.json` | Beer → the domains its logo is looked up from. |
| `data/untappd-averages.json` | The world's average per beer, for the contrarian chart. |
| `data/want-to-try.json` | The shortlist, each entry flagged `tried` and, when it has been, the name it was reviewed under. |

Nothing else in the repo reads `data/` — it exists so the data can leave.

## How the two repos fit together

```
  beer-review-buddy            Supabase              JWAL-BEER-REVIEW
  (add a beer, on a phone) ──> beers, breweries, ──> data.js ──> the site
                               locations, brand
                               domains, want-to-try
                                     │
                                     └── npm run sync, nightly in CI
```

The projection between the tables and `data.js` is written once, in
[`tools/supabase-rows.mjs`](tools/supabase-rows.mjs), and used in both
directions — so the seed that filled the database and the sync that reads it
back cannot disagree about what a column means. `npm run roundtrip` proves it on
every push, with no network: it sends the data out through the columns and back
and fails if a value does not survive.

Two brewery fields have no column behind them. `beers` (which beers a brewery
makes) and `ratings` (what each scored) are derived from the reviews, because a
beer row names its own brewery — a derived field cannot drift out of step with
the thing it mirrors.

## Hosting it somewhere else

The site is four static files; any static host serves it as-is. It has no
runtime dependency on Supabase: `data.js` is a plain script tag, so the page
works offline and keeps working if the database is unreachable.

`data/*.json` is table-shaped, one file per table, if you want the rows
somewhere else again.

To repaint from a different store at runtime instead, `data.js` declares
`beers`, `breweries` and `drunkLocs` with `let`: replace their contents from a
fetch and call `reloadData()` (in `app.js`). That function is the entire
integration surface.

Picking this repo up after a change of layout is covered in
[HANDOFF.md](HANDOFF.md).
