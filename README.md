# Jwal's Brew Reviews

A running log of every beer I drink — ratings, places and trends. A static site:
open `index.html` and it runs. There is no build step, no framework and no
server.

## The files

| File | What it is |
|------|------------|
| `index.html` | The page. Every panel's markup, and the three `<script>` tags. |
| `data.js` | **The store.** Every review, brewery, location and brand domain. No behaviour. |
| `app.js` | Everything the data does: stats, tables, charts, maps, search. No data. |
| `style.css` | The design system. `:root` is the only place a colour is written. |
| `data/` | Generated exports of `data.js` as JSON and CSV — see below. |
| `tools/` | Plain Node scripts. No dependencies, nothing to install. |
| `logos/` | Local logo files. `npm run logos -- --save` fills this from the CDNs so the logos stop depending on them. |

Chart.js and Leaflet load from a CDN, pinned to an exact version and locked to a
`integrity` hash, so a compromised CDN can't swap the library out.

## Working on it

Adding a beer is a data change: edit `data.js` following the procedure in
[CLAUDE.md](CLAUDE.md), then

```sh
npm run check     # every rule CLAUDE.md states, enforced
npm run export    # refresh data/ to match
```

`npm run check` needs nothing installed — it is Node and the repo. It runs on
every push (`.github/workflows/validate-data.yml`), so a beer with a country
code that has no flag, a brewery that was never registered or a missing brand
domain fails the build instead of quietly rendering wrong.

| Command | What it does |
|---------|--------------|
| `npm run check` | Validates the data and confirms `data/` is in step with `data.js` |
| `npm run export` | Regenerates `data/` from `data.js` |
| `npm run logos` | Checks what logo every beer actually resolves to, and at what resolution (needs the open internet) |
| `npm run sri` | Re-derives the CDN `integrity` hashes from npm (`-- --write` to fix them) |
| `npm run smoke` | Opens the page in a real browser and checks it works (needs `npm install`) |

## The data

`data.js` is the source of truth. `data/` holds the same rows in formats other
software can read, regenerated by `npm run export`:

| File | Shape |
|------|-------|
| `data/beers.json` · `.csv` | One row per pour. `beer` is not unique — the same beer drunk twice is two rows. |
| `data/breweries.json` · `.csv` | One row per brewery, with its beers and their ratings paired up. |
| `data/locations.json` · `.csv` | Every city a review was logged in, with coordinates. |
| `data/brand-domains.json` | Beer → the domains its logo is looked up from. |
| `data/untappd-averages.json` | The world's average per beer, for the contrarian chart. |
| `data/watchlist.json` | Beers not yet reviewed: the watchlist and the recommendation candidates. |

Nothing else in the repo reads `data/` — it exists so the data can leave.

## Hosting it somewhere else

The site is four static files; any static host serves it as-is.

To put the reviews in a database instead, import `data/*.json` — the JSON is
already table-shaped, one file per table, with `beers.beer` joining to
`breweries.beers[].beer` and `beers.city` + `beers.cc` joining to `locations`.

The page then needs one change and no more: `data.js` declares `beers`,
`breweries` and `drunkLocs` with `let`, so replacing their contents from a fetch
and calling `reloadData()` (in `app.js`) repaints the whole site from the new
rows. That function is the entire integration surface.
